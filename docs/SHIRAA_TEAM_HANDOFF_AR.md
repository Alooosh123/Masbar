# مِسبار — خطة تسليم الفريق وتشغيله ضمن شراع 2026

**المستودع:** https://github.com/Alooosh123/Masbar  
**الفرع العامل:** codex/misbar-mvp-hardening-2026-11-21  
**الفريق:** علاء، عادل، شهد، وفاء، سما  
**الهدف:** نموذج أولي قابل للتجربة والعرض؛ وليس نظاماً معتمداً لتنفيذ أعمال صيانة حقيقية.

## 1. الوضع الحالي للمستودع بعد الفحص

المستودع ليس قالباً فارغاً. يحتوي بالفعل على:

- Backend باستخدام FastAPI/Python.
- واجهة React 18 + TypeScript + Vite بهوية عربية RTL وPWA.
- جلسات صيانة، محادثة عربية، كاميرا، TTS عربي، WebSocket وسجل تدقيق.
- محرك سلامة حتمي يتضمن بوابة LOTO ورفض القطع غير المعروفة والثقة البصرية المنخفضة.
- محولات رؤية Cohere وOpenAI-compatible وMock، ومحولات محادثة وصوت.
- قاعدة معرفة JSON تجريبية: 9 قطع في 3 عائلات معدات (Caterpillar C15، Caterpillar 320D، Siemens S7).
- سجل OEM يضم أسماء شركات وعائلات موديلات وروابطها. هذا السجل لا يعني أن كتيبات الصيانة لكل موديل متوفرة أو مرخصة.
- اختبارات موجودة ونتائج محفوظة في docs/TEST_RESULTS.md وdocs/test-results/chat-e2e.json.

## 2. ما الذي تثبته الاختبارات الموجودة وما الذي لا تثبته؟

تقرير المستودع يسجل 64/64 اختبار pytest و34/34 فحص E2E. هذه نتائج موثقة داخل المستودع وليست نتيجة إعادة تشغيل لهذا الفرع بعد التعديلات.

حدود الاختبار المسجلة في التقرير:

- الكاميرا في E2E كانت بث canvas مُحقناً، وليست كاميرا هاتف حقيقية.
- الميكروفون كان جهازاً وهمياً صامتاً؛ لم يُختبر ASR بكلام عربي حقيقي.
- TTS تم فحص بدء تشغيله/تحميل ملف MP3؛ لكن لا يثبت ذلك جودة الصوت على كل جهاز.
- صورة التعرف الاصطناعية لا تثبت دقة النموذج على أجزاء صناعية حقيقية.
- بيانات الصيانة الحالية موسومة sample ولا تصلح لتوجيه فني لصيانة معدة فعلية.

## 3. التقييم التقني الصريح

| المجال | الموجود | الفجوة قبل الادعاء باكتماله |
|---|---|---|
| الواجهة العربية | موجودة وتُبنى عبر Vite | اختبار أجهزة حقيقية وإتاحة الوصول |
| الكاميرا | التقاط صورة ووضع وصف/تحديد | اختبار كاميرا فعلية وصور OEM متنوعة |
| الرؤية | VLM يختار من قائمة مرشحين مغلقة + Mock | Dataset موسوم وصور حقيقية ومقاييس precision/recall |
| قاعدة المعرفة | JSON تجريبية + فهرسة PDF محلية مصرح بها + بحث BM25/lexical مع مراجع صفحات | OCR وتحليل الجداول/الرسوم وQdrant/embeddings وNeo4j ما تزال غير منفذة؛ لا توجد بيانات صيانة Grundfos معتمدة بعد |

| المساعد العربي | محادثة عربية وتطبيع/مرادفات | اختبار لهجات وضوضاء بمقاطع صوتية حقيقية |
| الصوت | TTS عربي؛ إدخال الصوت عبر إمكانات المتصفح | ASR خادمي متين للمصانع غير منفذ |
| الواقع المكاني | Bounding box ثنائي الأبعاد وحقول تمهيدية | تثبيت مكاني 3D حقيقي وARCore/ARKit غير منفذ |
| الجلسات | SQLite محلي دائم مع TTL وسجل التدقيق واستعادة بعد إعادة التشغيل | نسخة واحدة/مضيف واحد؛ لا نسخ احتياطي آلي أو دعم عدة workers؛ يلزم تخزين مشترك عند التوسع |

## 4. ملاحظة سلامة تم إصلاحها في فرع العمل

كان backend/app/safety/guard.py يضع verified_from_manual=True لكل قيمة عزم حتى عندما تكون قاعدة المعرفة موسومة sample. كما أن الواجهة كانت تستخدم عبارة «عزم الشد المعتمد» دون التفريق في عنوان البطاقة.

تم تعديل ذلك في فرع العمل:

- القيمة لا تعتبر معتمدة إلا إذا كانت حالة ملف المعدة verified وحالة القطعة نفسها verified.
- أصبح الافتراضي في نموذج API هو false.
- تعرض الواجهة عنواناً مختلفاً للقيم التجريبية.
- يسجل سجل التدقيق torque_sample_shown بدلاً من torque_verified عند عرض قيمة غير معتمدة.
- أضيف اختبار يغطي بيانات sample وبيانات verified.

آخر تشغيل CI ناجح على `main` (commit `d0d729ab77335fa20e37a77092c4227f897a94b7`): **91 اختبار Backend ناجحاً**، وبناء Frontend نجح، و`npm ci` أظهر 0 vulnerabilities، وبُنيت صور Docker وشُغّلت الخدمتان. تحقق اختبار التشغيل من UID `10001` وجذر ملفات للقراءة فقط، واختبر API من نطاق الواجهة نفسه، ثم استعاد جلسة وسجل تدقيق بعد إعادة تشغيل Backend. تم الاختبار على GitHub Actions Linux runner وليس على خادم الإنتاج. اختبار E2E التاريخي 34/34 يستخدم كاميرا canvas وميكروفوناً وهميين، ولا يثبت التشغيل على هاتف فعلي. [نتيجة CI](https://github.com/Alooosh123/Masbar/actions/runs/45672867388).

## 5. توزيع الفريق بالأسماء

### علاء — قائد المنتج ومراجع المحتوى الصناعي
- يثبت نطاق العرض ويمنع إضافة ميزات خارج الوقت.
- يراجع هوية المعدة والموديل وإصدار الكتيب.
- يعتمد قاموس الأجزاء والمصطلحات العربية.
- يراجع التحذيرات والمراجع قبل نشر أي معلومة.
- يدير الاجتماعات ويجمع المخرجات ويقدم العرض.

**التسليم:** Project Definition Canvas، نطاق MVP، سجل المصادر والمخاطر، العرض النهائي.

### عادل — Backend والتكامل
- يفهم FastAPI ومسارات API الموجودة قبل تعديلها.
- يراجع نماذج الطلب/الاستجابة ويدير عقود الربط.
- يربط خدمة الرؤية ومحرك المعرفة والواجهة.
- يضيف اختبارات API ويصلح الأعطال.
- يمنع وضع أي مفتاح سري في Git.

**التسليم:** Backend متكامل، API موثق، اختبارات، سجل إعداد التشغيل.

### شهد — الرؤية الحاسوبية والبيانات المصورة
- تجمع صور أجزاء المعدات المصرح باستخدامها.
- تنشئ تصنيفاً واضحاً لكل جزء/موضع رسم.
- تفصل صور التدريب عن صور الاختبار.
- تختبر VLM الحالي على صور حقيقية، وتسجل الأخطاء والثقة.
- لا تضع وصفاً أو رقم جزء غير مؤكد ضمن بيانات الحقيقة الأرضية.

**التسليم:** Dataset منظم، قاموس الفئات، تقرير دقة/أخطاء، صور عرض مرخصة.

### وفاء — الكتيبات وقاعدة المعرفة والاسترجاع
- تسجل لكل وثيقة الشركة والطراز والإصدار والصفحات.
- تستخرج النص والجداول مع المحافظة على أرقام الصفحات.
- تميز بين part number وdrawing position.
- تضع status=sample إلى أن تتم مطابقة الموديل والمصدر والمراجعة.
- تختبر أسئلة بإجابات صحيحة وأسئلة يجب أن يرفضها النظام.

**التسليم:** سجل المصادر، فهارس محلية مرخصة غير مرفوعة إلى Git، تقرير جودة البحث ومراجع الصفحات، وأمثلة أسئلة/إجابات مع مراجع وحالات رفض.

### سما — الواجهة والكاميرا وتجربة الفني
- تفحص واجهة المحادثة الحالية قبل إضافة شاشات جديدة.
- تختبر RTL على الهاتف والحاسوب.
- تتحقق من أذونات الكاميرا والميكروفون وحالات الرفض.
- تعرض bounding box والمصدر والتحذير بوضوح.
- تسجل فيديو يوضح الرحلة الرئيسية.

**التسليم:** واجهة قابلة للتجربة، تقرير UX، لقطات، فيديو العرض.

## 6. طريقة العمل اليومية

1. اجتماع قصير 10–15 دقيقة: ماذا أنجزنا؟ ما العائق؟ ما مخرج اليوم؟
2. كل عضو يعمل على فرعه أو ملفاته دون الكتابة مباشرة على main.
3. كل تغيير يتضمن سبباً واختباراً أو طريقة تحقق.
4. يرفع العضو Pull Request أو يرسل التغيير للمراجعة.
5. لا تدمج تغييرات تمس السلامة أو مصدر العزم قبل مراجعتها.
6. في نهاية اليوم: نسخة تجريبية واحدة، قائمة أعطال، وقرار واضح لليوم التالي.

## 7. سياسة الفروع والتغييرات

- main هو الفرع المرجعي ولا يتم الدفع إليه مباشرة.
- استخدموا فروعاً قصيرة بأسماء مثل feature/vision-dataset وfix/api-validation.
- لا ترفعوا ملفات .env أو مفاتيح API أو تسجيلات صوتية خاصة.
- لا ترفعوا كتيبات OEM محمية أو غير مرخصة؛ احتفظوا بالرابط والبيانات المرجعية وحقوق الاستخدام.
- لا تفعّلوا `MANUAL_SEARCH_ENABLED=true` على خادم مكشوف للإنترنت قبل إضافة المصادقة والصلاحيات؛ Docker Compose يبقيه معطلاً.
- جميع PRs يجب أن تمر باختبارات Backend وبناء Frontend.
- عند تعارض الأكواد، لا تستبدلوا ملفاً كاملاً دون مراجعة الفروقات.

## 11. تحديث التخزين التشغيلي (21 نوفمبر 2026)

أضيفت طبقة SQLite اختيارية/افتراضية لحفظ الجلسات وسجل التدقيق واستعادتها بعد إعادة تشغيل الخادم مع TTL. تستخدم Docker volume باسم `misbar_sessions`. هذا يقلل فقد الجلسات في نموذج العرض على مضيف واحد، لكنه لا يحل التزامن بين نسخ متعددة أو النسخ الاحتياطي أو المصادقة؛ لا يزال التوسع يتطلب تخزيناً مشتركاً واختبارات استعادة وRBAC.


## 12. تقوية الحاويات والتحقق التشغيلي

أضيفت خطوة CI لبناء صور Docker وتشغيل Compose على Linux runner. يعمل Backend داخل الحاوية بمستخدم غير root UID 10001، وبجذر ملفات للقراءة فقط، مع إسقاط الصلاحيات غير المطلوبة ومجلدات بيانات دائمة محددة. يستبعد سياق البناء أسرار البيئة والكتيبات والفهارس النصية وقواعد SQLite وملفات الصوت والنسخ الاحتياطية.

اختبار runtime smoke تحقق من وصول الواجهة وBackend، ثم أنشأ جلسة عبر API وأعاد تشغيل Backend وتأكد من استرجاع الجلسة وسجل التدقيق من volume.

هذا لا يعني أن التطبيق نُشر على خادم إنتاج أو أنه تم اختبار هاتف ميداني، ولا يوفر النسخ الاحتياطي الآلي أو auth/RBAC. وتظل جميع سجلات قطع الصيانة الحالية sample.


## 13. تجهيز النشر السحابي الأولي

أضيفت إلى الفرع الرئيسي بنية تسمح بتشغيل Frontend وBackend كخدمتين منفصلتين داخل بيئة استضافة واحدة. يرسل المتصفح طلبات API وWebSocket إلى نطاق الواجهة نفسه، ويقوم Nginx بتمريرها عبر شبكة الخدمة الخاصة إلى Backend. يدعم كل من Nginx وUvicorn متغير `PORT` الذي تخصصه منصة الاستضافة.

- Backend: Dockerfile الجذر، منفذ داخلي 8000، وفحص صحة `/health`.
- Frontend: مجلد `web/` وNginx runtime template مع `BACKEND_UPSTREAM`.
- دليل إعداد Railway: `docs/RAILWAY_DEPLOYMENT_GUIDE_AR.md`.
- اختبار CI على main: 91 اختبار Backend، بناء الواجهة، بناء الصورتين، وصول API من نفس نطاق الواجهة واستعادة جلسة بعد إعادة تشغيل Backend.

**الحالة:** لم يتم ربط حساب Railway أو إنشاء مشروع وخدمات أو نطاق عام حتى الآن. ملف الإعداد جاهز، ويحتاج المستخدم إلى إكمال ربط حساب الاستضافة وGitHub ثم إنشاء الخدمات والمتغيرات.

**قيود العرض:** `VISION_PROVIDER=mock` و`CHAT_PROVIDER=off`، وكل بيانات الصيانة `sample`. لا تستخدم النسخة العامة لاتخاذ قرار صيانة صناعي.

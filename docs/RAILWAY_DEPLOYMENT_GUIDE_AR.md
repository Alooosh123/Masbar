# تشغيل مِسبار كنموذج سحابي أولي على Railway

## ما الذي ستنشره؟

هذا المستودع يحتوي خدمتين منفصلتين:

1. **Backend**: FastAPI على Dockerfile الموجود في جذر المستودع.
2. **Frontend**: React/Vite + Nginx في مجلد `web/`.

الواجهة ترسل طلبات `/api/*` و`/health` و`/ws/*` إلى Backend عبر Nginx، لذلك لا يحتاج المتصفح إلى الاتصال بمنفذ Backend منفصل ولا يحتاج كشف Backend على الإنترنت.

> **تحذير استخدام:** هذه نسخة عرض أولية. قطع المعرفة التسع في قاعدة البيانات موسومة `sample`، فلا تستخدم أي عزم أو خطوة صيانة لاتخاذ قرار صناعي حقيقي. يبقى بحث الكتيبات معطلاً إلى أن تُضاف المصادقة والصلاحيات ومصادر OEM المرخصة.

## قبل النشر

- حساب Railway متصل بحساب GitHub.
- صلاحية الوصول إلى مستودع `Alooosh123/Masbar`.
- إنشاء مشروع واحد في Railway وبيئة واحدة تحتوي الخدمتين.
- لا ترفع مفاتيح API إلى GitHub؛ أضفها فقط في Variables على المنصة عند الحاجة.

## 1. إعداد Backend

في Railway:

1. اربط الخدمة بالمستودع `Alooosh123/Masbar` والفرع `main`.
2. اجعل Root Directory هو جذر المستودع، وDockerfile Path هو `/Dockerfile`.
3. اضبط المتغيرات الأساسية:

| المتغير | القيمة |
|---|---|
| `ENVIRONMENT` | `production` |
| `PORT` | `8000` |
| `CORS_ORIGINS` | عنوان الواجهة بعد إنشائه، مثل `https://<frontend-domain>` |
| `VISION_PROVIDER` | `openrouter` لاستخدام NVIDIA Nemotron 3.5 Super VL المجاني عبر API، أو `cohere` / `openai` |
| `CHAT_PROVIDER` | `cohere` عند توفر مفتاح Cohere، أو `off` لتعطيل المحادثة العامة |
| `DEMO_MODE` | `false` |
| `MANUAL_SEARCH_ENABLED` | `false` |
| `SESSION_DB_PATH` | `/app/data/sessions/sessions.sqlite3` |
| `AUTH_REQUIRED` | `true` |
| `JWT_SECRET_KEY` | سر عشوائي لا يقل عن 32 حرفًا |
| `AUTH_TOKEN_TTL_MINUTES` | `480` |
| `BOOTSTRAP_ADMIN_EMAIL` | بريد حساب المالك الأول |
| `BOOTSTRAP_ADMIN_PASSWORD` | كلمة مرور أولية لا تقل عن 8 أحرف (يوصى بـ20 حرفًا أو أكثر لحساب المالك) |
| `RAILWAY_RUN_UID` | `0` عند استخدام Volume، لتهيئة صلاحياته فقط |

4. اجعل Healthcheck Path هو `/health`.
5. اترك Backend على الشبكة الخاصة؛ لا تنشئ له نطاقاً عاماً في النموذج الأولي.

### تخزين SQLite الدائم

استخدم الـVolume الدائم الموجود بالفعل في خدمة Backend باسم `masbar-sessions` واربطه بالمسار الدقيق التالي (لا تنشئ Volume آخر للخدمة نفسها):

```text
/app/data/sessions
```

Railway يركّب Volume مملوكًا لـroot. لذلك أضيف إلى صورة Backend مدخل تشغيل صغير يقوم عند بدء الحاوية بما يلي:

1. تجهيز مجلد الجلسات المركّب فقط.
2. تغيير ملكية مجلد الجلسات إلى UID/GID 10001.
3. خفض الصلاحيات فورًا وتشغيل FastAPI بصفة المستخدم غير المميّز 10001 عبر `gosu`.

يجب إبقاء `RAILWAY_RUN_UID=0` على خدمة Backend كي يعمل تهيئة المجلد؛ **عملية FastAPI نفسها يجب أن تعمل بـUID 10001**. لا تستخدم هذا المتغير دون مدخل التشغيل الذي يهبط بالصلاحيات.

لا توصل Volume قبل نشر هذه الصورة المعدّلة. بعد النشر، تحقق من:
- سجل التشغيل يثبت أن الخادم يبدأ بعد تجهيز المجلد.
- UID عملية التطبيق يساوي 10001.
- يمكن إنشاء جلسة واستعادتها بعد إعادة نشر Backend.
- ملف SQLite موجود داخل Volume وليس في طبقة الحاوية المؤقتة.

الـVolume الحالي حجمه 500MB ومربوط بالفعل بالخدمة. SQLite يظل مناسبًا لنسخة واحدة على مضيف واحد، وليس لتعدد النسخ أو المضيفين. لا تحذف Volume أو تعِد إنشاءه أثناء التحديث حتى لا تفقد الجلسات.

### نسخ SQLite الاحتياطي

يمكن تفعيل لقطة عند بدء الحاوية من Backend عبر SQLITE_BACKUP_ON_STARTUP=true، مع SQLITE_BACKUP_DIR=/app/data/sessions/backups وSQLITE_BACKUP_RETENTION_DAYS=14. يتم إنشاء اللقطة بعد تهيئة قاعدة البيانات والتحقق منها، وتبقى داخل Volume الحالي. لأن خيار Sleep مفعّل، لا تعتبر هذه جدولة يومية ثابتة أو نسخة خارجية.

### المصادقة وحساب المالك الأول

يستخدم المشروع حاليًا نظام المصادقة الموجود على `main`، وليس تسجيل دخول مبنيًا على Local Storage:

- جلسة الدخول تحفظ في Cookie من نوع HttpOnly وSecure في الإنتاج.
- يتم تخزين كلمات المرور بصيغة PBKDF2 مع salt.
- بعد خمس محاولات فاشلة، يتم تعليق الدخول لمدة 15 دقيقة.
- الأدوار المعتمدة: `owner` و`admin` و`technician` و`viewer`.
- ينشئ الخادم حساب المالك الأول مرة واحدة من `BOOTSTRAP_ADMIN_EMAIL` و`BOOTSTRAP_ADMIN_PASSWORD` إذا لم يوجد أي مستخدم في قاعدة `SESSION_DB_PATH`.
- الحد الأدنى المقبول لكلمة المرور الأولية 8 أحرف، ويوصى باستخدام 20 حرفًا أو أكثر لحساب المالك. بعد إنشاء الحساب بنجاح يمكن إزالة متغير كلمة المرور الأولية من Railway للحماية.

لا توجد صفحة تسجيل عام. لا تفعّل `AUTH_REQUIRED=true` قبل ضبط `JWT_SECRET_KEY` وبيانات حساب المالك الأول وعنوان الواجهة في `CORS_ORIGINS`.

## 2. إعداد Frontend

1. اربط الخدمة بالمستودع نفسه وعلى الفرع `main`.
2. اجعل Root Directory هو `/web`.
3. Dockerfile Path هو `/web/Dockerfile` إذا كان الحقل يطلب المسار من جذر المستودع، أو `Dockerfile` إذا كان نسبيًا إلى Root Directory.
4. أضف:

```env
BACKEND_UPSTREAM=http://<backend-private-domain>:8000
```

استخدم نطاق Backend الخاص داخل Railway، بالشكل `<service-name>.railway.internal`. لا تستخدم النطاق العام للـBackend في هذا المتغير.

5. لا تضبط `VITE_API_URL`؛ الواجهة الإنتاجية تستخدم نطاقها الحالي وترسل الطلبات إلى Nginx.
6. أنشئ Public Domain لخدمة Frontend.

## 3. تفعيل مزود الرؤية عبر API

يدعم MISBAR الآن NVIDIA Nemotron 3.5 Super VL المجاني عبر OpenRouter باستخدام واجهة OpenAI-compatible. لا يحتاج Backend إلى تثبيت Ollama أو تنزيل أوزان النموذج؛ يرسل الصورة إلى خدمة API من الخادم فقط.

أضف المتغيرات التالية في Backend داخل Railway أو في ملف `.env` المحلي:

```env
VISION_PROVIDER=openrouter
OPENROUTER_API_KEY=<secret>
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
VISION_MODEL=nvidia/nemotron-3.5-super-vl:free
VISION_TIMEOUT_SECONDS=60
DEMO_MODE=false
```

اترك `VISION_MODEL` فارغًا لاستخدام الطراز الافتراضي أعلاه. مفتاح OpenRouter سرّ خاص بالـBackend؛ لا تضعه في الواجهة أو Git أو ترسله في المحادثة. لا يلزم `COHERE_API_KEY` لمسار تحديد المعدات أو القطع عند اختيار OpenRouter.

المحادثة العامة إعداد منفصل عن تحديد الصور:
- اضبط `CHAT_PROVIDER=cohere` و`COHERE_API_KEY` فقط إذا أردت الإبقاء على خدمة محادثة Cohere.
- اضبط `CHAT_PROVIDER=off` إذا لم يكن لديك مزود محادثة. تظل بوابة الصيانة والبحث المقيد منفصلين عن الدردشة العامة.

الطلب يذهب إلى `POST https://openrouter.ai/api/v1/chat/completions` مع صورة Base64 واسم النموذج. لا توجد خدمة Ollama أو ملفات نماذج محلية مطلوبة.

**التكلفة والحدود:** تعرض OpenRouter نسخة `nvidia/nemotron-3.5-super-vl:free` بسعر صفر لرموز الإدخال والإخراج. لكنها خاضعة لحدود الاستخدام والتوفر وقد تتغير الحصص أو آلية التوجيه؛ قد يرجع المزود `429` عند بلوغ الحد. راجع صفحة النموذج الحالية قبل الاعتماد التشغيلي.

بعد الإعداد، افحص `GET /health` واختبر صورة فعلية معروفة. وجود المفتاح أو نجاح الاختبارات الوهمية لا يثبت نجاح الاتصال أو دقة التعرف. لا ترسل صور المعدات إلى مزود خارجي قبل مراجعة سياسة الخصوصية.

**الخصوصية:** عند تفعيل مزود سحابي، ترسل الصور الملتقطة إليه. لا ترسل صور معدات العملاء قبل مراجعة سياسة الاحتفاظ والخصوصية والحصول على الموافقات المناسبة.

## 4. قاعدة المعرفة الصناعية

- سجل OEM الحالي يضم روابط وموديلات مصادر الشركات فقط؛ هذا لا يعني أن كتيبات الخدمة نفسها متاحة.
- بيانات الصيانة التسع في المشروع ما زالت `sample`.
- لا تفعّل بحث مقتطفات الكتيبات في الخدمة العامة قبل المصادقة وRBAC.
- لا تعتمد عزمًا أو خطوة فك/تركيب أو LOTO من دون كتيب أصلي مرخص ومراجعة فنية مستقلة.
- مسار التحقق يتطلب مرجع الوثيقة ومراجعتها وSHA-256 والصفحة والموديل ومراجعين مختلفين ونطاقات مراجعة واضحة. تحقق التطبيق من اتساق هذه البيانات ولا يثبت وحده أصالة الكتيب أو كفاءة المراجع.

## 5. اختبار الكاميرا والميكروفون

اختبارات Chrome الآلية الحالية تستخدم كاميرا canvas وميكروفونًا وهميين؛ لا تمثل اختبار جهاز ميداني.

الاختبار الحقيقي يجب أن يتم من هاتف أو حاسوب فعلي عبر HTTPS:
- السماح للمتصفح باستخدام الكاميرا الخلفية.
- التقاط صورة ومراجعة دقتها وإرسالها إلى Backend.
- السماح بالميكروفون، والتحدث بالعربية، والتحقق من ظهور النص الصحيح.
- اختبار انقطاع الشبكة ورفض الإذن وإعادة المحاولة.
- التأكد من عدم حفظ الصورة أو الصوت أو مشاركتهما خارج السياسة المعتمدة.

لا يمكن تنفيذ منح أذونات جهازك أو قياس الكاميرا والميكروفون عليه من خادم Railway نيابةً عن متصفحك.

## 6. فحوص النشر

- `https://<frontend-domain>/` يعرض صفحة مِسبار.
- `https://<frontend-domain>/health` يعرض `status=online`.
- `https://<frontend-domain>/api/v1/equipment` يعيد المعدات.
- بعد تفعيل المصادقة، يجب أن تُرفض طلبات الجلسات والكتيبات غير المصادق عليها.
- لا تستخدم النسخة الحالية لتوجيه صيانة معدات حقيقية ما دامت بيانات OEM موسومة `sample`.

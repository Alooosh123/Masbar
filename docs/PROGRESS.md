# سجل تقدم مِسبار

## 3.10 بوابة اعتماد موثقة لبيانات قاعدة المعرفة وضبط CORS (21 نوفمبر 2026)

**ما أضيف على فرع التطوير:**

- أصبح ضبط ملف المعدة إلى `data_status=verified` يتطلب `equipment_verification_evidence`، ومطابقة الموديل، ونطاق مراجعة الهوية.
- أصبح ضبط القطعة إلى `verification_status=verified` يتطلب `verification_evidence` مطابقاً لمعرف الدليل والصفحة والموديل.
- يجب تسجيل SHA-256 للمصدر، رقم الوثيقة ومراجعتها، مرجع لوحة بيانات داخلي، نطاقات المراجعة، وقتين مزودين بمنطقة زمنية، ومعرفي مراجع/معتمد مختلفين.
- لا يمكن اعتماد قيم العزم دون مراجعة نطاق `torque`؛ ولا يمكن اعتماد سجل ذي LOTO/تحذيرات دون مراجعة نطاق `safety`.
- حُدّث `SafetyGuard` حتى لا يعتبر مجرد تغيير حقول الحالة اعتماداً للعزم، وحتى يعيد `source_status=sample` عندما تفشل بوابة الدليل.
- تمت إضافة اختبارات رفض البيانات التي تفتقد دليلاً أو تخالف الصفحة/الموديل/نطاقات المراجعة.
- تم منع wildcard CORS في بيئة الإنتاج، مع تغيير الإعداد الافتراضي في Docker Compose إلى أصل محلي محدد بدلاً من `*`.

**الحدود:** تحقق التطبيق من اتساق بيانات الدليل المسجلة، لكنه لا يثبت وحده أصالة PDF أو مطابقة SHA-256 للملف الأصلي، ولا يثبت كفاءة المراجع أو صحة المعلومة الفنية. لا توجد حالياً بيانات صيانة فعلية مرقاة إلى verified؛ تظل بيانات المشروع الحالية sample.

تفاصيل الاستخدام: `docs/VERIFIED_KB_REVIEW_AR.md`.

## 3.11 حفظ الجلسات واستعادتها عبر SQLite (21 نوفمبر 2026)

- إضافة SQLite محلي لحفظ بيانات الجلسة وسجل التدقيق بدلاً من فقدهما عند إعادة تشغيل العملية.
- حفظ حالة الجلسة والمعدة والقطعة وتفاصيل التحديد وLOTO وبنود التأكيد والخطوة وسجل التدقيق والطوابع الزمنية.
- استعادة الجلسات غير المنتهية عند بدء الخادم، وتطبيق TTL وحذف السجلات المنتهية.
- إضافة `SESSION_DB_PATH` مع إبقاء إمكانية وضع الذاكرة للاختبارات أو التشغيل الذي لا يحدد قاعدة.
- إضافة اختبارات لإعادة التشغيل، واستعادة حالة الجلسة وسجل التدقيق، وانتهاء الصلاحية، والوضع المؤقت في الذاكرة.
- إضافة Docker named volume باسم `misbar_sessions` حتى لا ترتبط قاعدة الجلسات بعمر الحاوية.

**الحدود:** SQLite مناسب لتطبيق واحد على مضيف واحد. لا يوفر هذا التغيير تخزيناً مشتركاً متزامناً لعدة workers أو hosts، ولا نسخاً احتياطياً مجرباً أو مصادقة/RBAC. لا تعتبره وحده جاهزاً للإنتاج متعدد المستخدمين.

## 3.12 تقوية صور Docker واختبار تشغيلها واستعادة الجلسات (21 نوفمبر 2026)

- تشغيل Backend داخل الصورة بمستخدم نظام غير root: UID/GID 10001.
- تفعيل `read_only: true` لجذر نظام الملفات، مع `tmpfs` محدود لـ `/tmp`، وإسقاط Linux capabilities ومنع اكتساب صلاحيات جديدة.
- تخصيص volumes دائمة لقاعدة جلسات SQLite وذاكرة TTS، وإبقاء مجلد فهارس الكتيبات للقراءة فقط.
- توسيع `.dockerignore` لمنع إدراج ملفات `.env` والكتيبات المحلية والفهارس النصية وقواعد SQLite وملفات الصوت والنسخ الاحتياطية في صورة التطبيق.
- تحديث CI ليبني صور Backend وFrontend فعلياً، ثم يشغّل Compose ويختبر `/health` والواجهة وهوية المستخدم وصلاحية نظام الملفات.
- اختبار جلسة حقيقي عبر API: إنشاء جلسة، إعادة تشغيل حاوية Backend، ثم استرجاع الجلسة وسجل التدقيق والتحقق من حدث `session_created`.
- تقوية معرفات الجلسات باستخدام `secrets.token_urlsafe(32)`، مع اختبار لطول الرمز وعدم تكرار المعرفات ضمن العينة.

## 3.13 تجهيز النشر السحابي مع واجهة API من نفس النطاق

- تعديل API URL: في Vite development يستمر الاتصال المحلي على المنفذ 8010؛ في production تستخدم الواجهة نطاقها الحالي.
- نقل Nginx من ملف إعداد ثابت إلى قالب Runtime يستقبل `PORT` و`BACKEND_UPSTREAM`.
- إضافة تمرير داخلي لمسارات `/api/` و`/health` و`/ws/` عبر Nginx إلى Backend.
- جعل Backend يستمع على متغير `PORT` مع افتراضي 8000، وإبقاء فحص صحة Docker متوافقاً مع المنفذ.
- توسيع Docker Compose لتحديد `PORT` و`BACKEND_UPSTREAM` محلياً.
- توسيع CI لاختبار الصحة وقائمة المعدات عبر نطاق الواجهة نفسه، وإنشاء جلسة واستعادتها بعد إعادة تشغيل Backend عبر وسيط Nginx.
- إضافة دليل Railway بالعربية لخدمتين داخل مشروع واحد، مع إبقاء Backend على Private Networking.

**نتيجة التحقق:** دمج PR #2 على main. CI النهائي على main نجح: 91 اختبار Backend، بناء Frontend، صفر ثغرات npm، بناء الصورتين، اختبار API من نفس نطاق الواجهة واستعادة الجلسة بعد إعادة التشغيل.

**الحالة:** ملفات الإعداد ودليل النشر موجودة على main. يلزم ربط Railway بحساب GitHub وإنشاء الخدمات والنطاقات. لم يتم حتى الآن إنشاء مشروع Railway أو نشر نسخة دائمة.

**القيود:** العرض يستخدم `VISION_PROVIDER=mock` و`CHAT_PROVIDER=off` ولا يحتوي على بيانات صيانة معتمدة أو مصادقة/RBAC. قاعدة SQLite تحتاج إلى Volume دائم مع التحقق من صلاحيات UID 10001 أو إلى ترحيل لقاعدة بيانات مشتركة قبل الاعتماد الإنتاجي.


## 3.14 تفعيل Cohere والتحقق من جاهزية الرؤية وتوثيق المسارات الميدانية

**المضاف على هذا الفرع:**

- أضيف الحقل `vision_ready` إلى `/health` ليبيّن توفر إعدادات مفتاح مزود الرؤية. هذا مؤشر إعداد فقط وليس اختبارًا فعليًا لاستجابة Cohere.
- تم اختيار Cohere للرؤية والمحادثة على Railway باستخدام سر `COHERE_API_KEY` داخل متغيرات Backend فقط؛ لم يُحفظ أي مفتاح في GitHub.
- تمت المحافظة على نظام المصادقة الموجود مسبقًا على `main`، بما فيه Cookie آمن HttpOnly، وPBKDF2، وقفل محاولات الدخول، وأدوار owner/admin/technician/viewer. لم تتم إضافة نظام دخول موازٍ.
- وثيقة `docs/OEM_REVIEW_WORKFLOW_AR.md` تشرح مراجعة مستقلة من شخصين، وبصمة SHA-256، ومطابقة الموديل والصفحة والنطاق الفني قبل الاعتماد.
- وثيقة `docs/REAL_DEVICE_TEST_CHECKLIST_AR.md` تشرح اختبار الكاميرا والميكروفون على هاتف/حاسوب فعلي عبر HTTPS.

**التخزين والنشر:**

- يوجد بالفعل Volume باسم `masbar-sessions` مربوط بخدمة Backend على `/app/data/sessions`، حجمه 500MB. يجب الإبقاء عليه دون حذف أو استبدال.
- تتشارك الجلسات والمستخدمون ملف SQLite نفسه تحت هذا المسار.
- صورة Backend تحتوي مدخل تشغيل يجهز ملكية مجلد Volume ثم يخفض عملية FastAPI إلى UID 10001.
- متغيرات إعداد Cohere والمصادقة محفوظة في Railway؛ يجب أن تستخدم أسماء المصادقة المتوافقة مع التنفيذ الحالي: `AUTH_REQUIRED` و`JWT_SECRET_KEY` و`BOOTSTRAP_ADMIN_EMAIL` و`BOOTSTRAP_ADMIN_PASSWORD`.

**القيود المتبقية:**

- قيمة `vision_ready` تؤكد وجود المفتاح في الإعدادات فقط؛ لم نثبت بعد نجاح اتصال Cohere بمحادثة فعلية ووصف صورة حي.
- بيانات الصيانة التسع الحالية ما زالت `sample`؛ لم تُرفق كتيبات OEM أصلية مرخصة ولم تُعتمد قيم عزم أو LOTO جديدة.
- لا يمكننا منح أذونات كاميرا/ميكروفون جهازك عن بُعد؛ اختبار الأجهزة الفعلية ينتظر تنفيذ قائمة التحقق من متصفح الجهاز نفسه.
- لا تعد هذه النسخة معتمدة للتوجيه الصناعي قبل استكمال مراجعة OEM والاختبار الميداني.

# تدقيق واستقرار نسخة MVP — مِسبار

**الغرض:** توثيق نطاق الإصلاحات البرمجية وحدود النسخة، دون اعتبار هذا المستند اعتماداً هندسياً للمعدات.

## ما يطبقه المشروع فعلياً

- الواجهة: React + TypeScript + Vite.
- الخادم: FastAPI.
- تحديد الصورة: Cohere Vision يختار من قائمة القطع المرشحة للمعدة المحددة؛ هذا ليس YOLO أو OpenCV ولا نموذج كشف عام.
- المحادثة العامة ووصف الصور: Cohere Chat v2.
- تعليمات التشغيل: محرك Python حتمي يقرأ سجلات data/kb، وليس إجابة حرة من نموذج المحادثة.
- فهرسة الكتيبات: فهرس محلي BM25 نصي مع بيانات مستند وصفحات PDF والصفحات المطبوعة. لا يوجد Qdrant أو بحث متجهي أو تضمينات أو OCR ضمن مسار النسخة الحالي.

## تغييرات الاستقرار

1. لا تعود قيم العزم التجريبية قابلة للعرض. يعيد محرك السلامة قيمة العزم فقط عندما تكون القطعة والمعدة موثقتين بأدلة متطابقة، ويشمل نطاق المراجعة identity وprocedure وtorque.
2. لا تظهر خطوات الصيانة أو مرجع الكتيب في استجابة الجلسة إلا بعد اجتياز بوابة المصدر والمعدة. لا يكفي تغيير data_status وحده.
3. لا يمكن تأكيد LOTO أو تشغيل خطوة عند غياب مراجعة هوية القطعة وإجراءات السلامة من مصدر مطابق. تعرض الواجهة حالة إيقاف آمن ولا تعرض checklist تجريبية.
4. يضيف رد API حقولاً صريحة لحالة توفر الإجراء والامتناع وسببه.
5. تمر مخرجات نموذج المحادثة ووصف الصور عبر حارس خادمي يرفض علامات التحليل أو التعليمات الداخلية. عند الرفض يمتنع النظام بدلاً من عرض النص الخام.
6. تعيد أخطاء المحادثة غير المعالجة رسالة خدمة آمنة برمز 503، وتبقى تفاصيل الاستثناء في سجل الخادم.
7. يبدأ التعرف الصوتي مباشرة داخل تفاعل زر الميكروفون، ويستخدم وضع الاستماع المستمر، ولا يرسل النص إلا بعد ضغط المستخدم زر الإيقاف.
8. تحسن تنسيقات CSS تخطيط رأس المحادثة والفقاعات وأدوات الإدخال عند الشاشات الضيقة، مع قواعد منفصلة للهاتف واللوحي.

## حدود قاعدة المعرفة والكتيبات

- تحتوي قاعدة البيانات الحالية على **9 سجلات تجريبية** موزعة على ثلاثة عائلات معدة. هذا العدد أكبر من هدف MVP المذكور (ثلاثة مكونات كحد أقصى). لم تُحذف سجلات موجودة أو يُخترع اختيار أي ثلاثة منها؛ يلزم حسم القطع الثلاث النهائية قبل تقليص البيانات.
- السجلات الحالية sample وليست إجراءات صيانة معتمدة؛ لذلك ستظل خطوات التشغيل والعزوم محجوبة حتى إدخال مراجعة مستقلة صحيحة.
- فهرس الكتيبات الفعلي لا يضم مستندات الإنتاج حالياً؛ مجلد data/manual_index لا يحوي إلا ملف الحفظ .gitkeep في مستودع المصدر، كما تستثني إعدادات Git وDocker ملفات الفهرسة المحلية.
- الدليل Siemens S7-1200 V4.7 ودليل Grundfos CR 1/3/5 Model A المرفقان تمت مراجعتهما كمصدرين نصيين، لكنهما لم يُدخلا في فهرس الإنتاج، ولم تُسجل موافقة حقوق المعالجة/النشر المطلوبة في أداة الاستيراد. كما أن Grundfos Model A يخص عائلة مضخات غير موجودة ضمن العائلات الثلاث الحالية، لذلك لم نضف دعماً لها.
- دليل Siemens لا يحدد عزماً عاماً لأطراف لوحة تحكم أو كونتاكتور؛ لذلك لا يجوز استنتاج عزم للوحة من هذا الدليل.
- دعم الصفحات المصورة/الممسوحة يحتاج OCR مرخصاً ومراجعة؛ صفحات بلا نص قابل للاستخراج لن تُفهرس تلقائياً.

## تفسير رموز API

- 401 من /api/v1/auth/login عند إدخال بيانات غير صحيحة هو سلوك مصادقة صحيح، وليس سبباً لتعطيل الحماية.
- سجلات Railway التي تمت مراجعتها أظهرت /health و/api/v1/auth/me و/api/v1/chat وطلبات Cohere ناجحة (200) أثناء فترة النشاط، ثم دخلت خدمتا الواجهة والخادم وضع النوم عند الخمول. لذلك لم يثبت وجود عطل ثابت يفسر كل 502؛ قد يظهر 502 أثناء نوم الخدمة أو استيقاظها. لا ينبغي تعطيل المصادقة أو تضمين أسرار في الواجهة لمعالجة ذلك.
- الـWeb Speech API لا يعمل في كل متصفح أو إعداد جهاز. عند عدم دعمه أو رفض الإذن يجب أن يبقى إدخال النص متاحاً.
- لا يمكن اعتماد سرعة تحديد 10 ثوانٍ أو سلامة الميكروفون أو الكاميرا دون اختبار ميداني على متصفح وجهاز فعليين.

## ما يجب أن يسبق اعتماد إجراءات فعلية

1. اختيار ثلاثة مكونات MVP النهائية من السجلات القائمة، أو تأكيد بقاء النطاق كما هو.
2. توفير إثبات حق معالجة الكتيبات المراد فهرستها.
3. فهرسة الكتيبات المطابقة للطراز مع حفظ رقم صفحة PDF ورقم الصفحة المطبوعة كلٌّ على حدة.
4. مراجعة مهندس/فني مؤهل واعتماد مستقل لنطاق الهوية والإجراء والعزم والسلامة قبل تغيير أي سجل إلى verified.
5. اختبار الكاميرا والميكروفون والجلسة من أجهزة فعلية، واختبار Railway بعد استيقاظ الخدمة.

**ملاحظة:** لا تمنح هذه الإصلاحات موافقة تشغيلية للمعدة؛ هي تجعل التطبيق يمتنع عند غياب الأدلة بدلاً من عرض بيانات نموذجية كتعليمات معتمدة.
